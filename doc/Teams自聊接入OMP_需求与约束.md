# Teams 自聊接入 OMP：需求与约束汇总

整理日期：2026-10-01（Asia/Tokyo）  
项目目录：`<PROJECT_DIR>`  
文档性质：对当前讨论的需求、已确认规则、可行性判断和未决事项进行汇总；不是已完成的服务设计或实现说明。

## 1. 目标与范围

将 Teams 自聊窗口的消息读取、发送、修改和删除能力封装为本地服务，对外提供 Telegram Bot API 风格的接口，接入 OMP 的 Telegram 插件，使用户能够通过 Teams 自聊窗口与 OMP 交互。

用户最初希望请求格式、消息和事件与 Telegram Bot API 完全一致。实际落地以兼容所选 OMP Telegram 插件的调用和事件消费方式为目标；Teams 与 Telegram 的界面和事件模型存在差异，不能直接承诺全部能力及语义完全一致。差异应通过明确的映射、功能限制或必要的插件适配处理。

当前讨论的主要范围为：

- 一个当前账号的 Teams 自聊窗口作为用户交互入口。
- 本地常驻服务采集用户指令，并在同一个自聊窗口输出 OMP 回复。
- Telegram 风格的请求、响应和更新事件兼容层。
- 将 Telegram 按钮选项转换成用户可发送的选择指令。
- 保留 OMP 原有指令，通过 `/chat /对应指令` 的形式调用。
- 消息身份映射、去重、来源识别和重启恢复。
- Teams 消息修改、删除与 OMP 行为之间的边界。

SharePoint 文件传输已进行单独验证并形成技能，可作为未来文件能力的候选底层；尚未确定必须在桥接服务第一版中集成。

## 2. 已确认的用户交互规则

### 2.1 用户提交任务：`/chat`

- 用户发来的任务消息必须在正文开头带 `/chat`。
- 服务移除 `/chat` 前缀，将任务正文作为用户消息交给 OMP。
- 没有任务前缀、也不是有效选择指令的普通消息不交给 OMP处理。
- 不因消息内容看起来像问题、任务或命令就自动执行。

示例：

```text
/chat 检查项目并给出修改建议
```

交给 OMP 的正文为：

```text
检查项目并给出修改建议
```

`/chat` 与正文之间的空白、大小写、空正文、换行及边界匹配方式需要在实现前定稿，避免 `/chatting` 等文本被误判成指令。

### 2.2 用户操作选项：`/choose`

用户要求将 Telegram 的按钮选项指令化：需要用户选择时，把选项转换成对应指令，追加在回复消息后面；用户发送对应指令即代表选择对应选项。

讨论中采用的指令格式为：

```text
/choose <菜单编号> <选项编号>
```

示例：

```text
/choose k7 1
```

- `/choose` 是独立的选择入口，不要求再套一层 `/chat`。
- 菜单编号用于区分不同问题和旧菜单；不能仅凭 `/1`、`/2` 或 `/yes` 判断选择对象。
- 选项映射由确定性程序完成，不调用模型猜测用户选择含义。
- 对于使用 `callback_data` 的按钮，保留原始值并转换为对应的 Telegram `callback_query`。
- URL、Web App 等不使用 `callback_data` 的其他按钮类型尚未确定支持方式，不能一律伪造为回调按钮。

### 2.3 OMP 回复：`omp：`

用户明确要求 OMP 回复统一带标签：

```text
omp：回复正文
```

- 前缀为小写 `omp` 和全角冒号 `：`。
- 编辑已发送的 OMP 回复时保留该前缀。
- 选项指令追加在相应回复的正文后面。
- 只解析消息正文开头的输入指令；回复中引用的 `/chat`、代码示例或列出的 `/choose` 不能触发输入。
- OMP 回复不重新进入 OMP 的用户消息队列。

完整示例：

```text
用户消息：
/chat 检查项目并给出修改建议

服务回复：
omp：检查完成，是否应用修改？
应用：/choose k7 1
取消：/choose k7 2

用户消息：
/choose k7 1

服务回复：
omp：已应用修改。
```

上例展示消息格式，不构成对真实项目修改的执行授权。

### 2.4 输入分类

| 消息类型 | 处理方式 |
|---|---|
| `/chat` 后为普通正文的用户消息 | 移除外层前缀后转换为任务输入 |
| `/chat` 后为原有 `/指令` 的用户消息 | 移除外层前缀后交给原有指令分发机制，保留名称及参数 |
| 正文开头为有效 `/choose` 的用户消息 | 查找菜单映射并生成选择回调 |
| 服务发出的 `omp：` 回复 | 输出消息，不生成用户输入事件 |
| 其他普通消息 | 忽略，不触发 OMP |
| 无效、过期或重复的选择指令 | 按菜单规则处理，不误执行其他选项 |

无效选择的具体提示文字尚未定稿。

### 2.5 保留 OMP 原有指令

用户追加的明确需求：OMP 原有指令应保留，用户在 Teams 自聊中的调用格式改为：

```text
/chat /对应指令 [原有参数]
```

- 桥接层只移除外层 `/chat` 及约定的分隔空白，不移除内部指令的 `/`，不重命名指令或改写参数。
- 普通任务正文与内部指令均使用 `/chat` 作为入口；未经 `/chat` 包裹的原有指令不触发 OMP。独立 `/choose` 仍按既有规则处理。
- 内部指令必须进入相应的原有指令分发机制，不能仅当作普通模型提示，让模型模拟执行控制指令。
- 指令生成的回复同样统一加 `omp：`；如产生选项，继续追加对应 `/choose` 指令。
- 如果所选插件依赖 Telegram 消息 entities 识别 bot_command，兼容层应按移除前缀后的正文重新生成实体及偏移，不能复用 Teams 原文的偏移。实体偏移和长度遵循 Telegram 的 UTF-16 计数规则。

格式示例（实际是否支持以下指令，以最终所选插件和 OMP 版本核验为准）：

| Teams 输入 | 分发给插件／OMP 的内容 |
|---|---|
| `/chat /status` | `/status` |
| `/chat /model 原有参数` | `/model 原有参数` |
| `/chat /stop` | `/stop` |

可行性边界：保留指令文本和路由是可实现的，但 Telegram 插件的指令集合不一定等于 OMP 终端全部指令。最终需清点原有指令：插件已有支持的继续使用原路径；未暴露到 Telegram 入口的 OMP 指令，需要补充调用适配，或明确说明限制，不能声称仅去掉 `/chat` 就已保留全部能力。具体指令清单及需要终端交互的指令如何处理尚未确定。

## 3. 拟采用的整体结构

```mermaid
flowchart LR
    U[用户在 Teams 自聊发送指令] <--> T[Teams 网页]
    T <--> W[本地浏览器适配器]
    W <--> S[消息映射与持久化队列]
    S <--> A[Telegram Bot API 兼容服务]
    A <--> P[OMP Telegram 插件]
    P <--> O[OMP]
```

上述结构是讨论中提出的实现方向，尚未确定具体语言、框架、进程拆分、端口、数据库或部署方式。

- 浏览器适配器负责 Teams 页面中的实际操作与状态采集。
- 消息和队列层负责身份映射、版本、去重、来源、处理状态及恢复。
- API 兼容层接受 OMP 插件的 Telegram 风格调用，并返回对应结果或更新事件。
- OMP 及其插件继续负责模型交互、任务队列和任务执行。
- 浏览器操作宜由确定性程序完成，无需每次使用模型决定如何点击页面。

本地服务不等于完全离线：Teams 仍依赖微软服务；OMP 使用的模型和网络边界取决于其配置，尚未在本次讨论中确定。

## 4. OMP 插件选择与接入约束

用户希望采用“最常见的” OMP Telegram 插件，但尚未确认具体仓库、版本或已安装的包。

分析参考了以下实现：

- [llblab/pi-telegram](https://github.com/llblab/pi-telegram)：Pi Telegram 适配器上游。
- [evandrodevbr/oh-my-pi-telegram](https://github.com/evandrodevbr/oh-my-pi-telegram)：面向 OMP 的适配版本。

这两个项目是分析依据，不代表已证实其使用量最高，也不代表已选定其中一个。实现前应固定实际插件及版本，再列出它真正调用的方法和消费的事件。

已检查的传输代码将 `https://api.telegram.org` 作为固定 API 地址，涉及普通请求、机器人身份校验、文件上传和文件下载。因此不能认为只配置一个本地 token 就能接入本地服务。

拟给插件新增可配置的服务地址，并覆盖所有相关传输路径。例如：

```text
API 地址：http://127.0.0.1:8765
Token：本地服务访问密钥
```

以上地址、端口和配置名称仅为示例，不是已确定的产品配置。需要一并处理 HTTP/HTTPS 传输，避免改了普通请求地址而身份校验、文件请求或回退路径仍访问 Telegram。

本方案可使用本地虚拟机器人身份与访问密钥，真实 Telegram bot、真实 Telegram token 和真实 Telegram 网络连接不应成为消息桥接本身的必需条件；插件是否还有额外依赖需核验。

源码依据：

- [OMP 适配版本的传输代码](https://github.com/evandrodevbr/oh-my-pi-telegram/blob/main/lib/telegram-api.ts)
- [上游传输代码](https://github.com/llblab/pi-telegram/blob/main/lib/telegram-api.ts)

## 5. Telegram API 兼容目标与差异

拟兼容的请求路径形态：

```text
/bot<token>/<METHOD_NAME>
```

响应使用 Telegram 风格的 `ok`、`result`、`description` 和错误信息。具体字段、HTTP 方法、参数编码方式和必填条件，应以所选插件及 [Telegram Bot API 文档](https://core.telegram.org/bots/api) 为准。

| 能力 | 拟映射方式 | 当前边界 |
|---|---|---|
| `getMe` | 返回本地虚拟机器人身份 | 可实现，身份字段需满足插件要求 |
| `getUpdates` | 从持久化更新队列返回用户指令与选择事件 | 需实现 offset、过滤和长轮询等实际调用语义 |
| `sendMessage` | 在 Teams 自聊发送带 `omp：` 的回复 | 网页发送已有实测基础 |
| `editMessageText` | 编辑映射到的 OMP 回复 | Teams 编辑操作尚未实测 |
| `deleteMessage` | 删除映射到的 OMP 回复 | Teams 删除操作尚未实测 |
| `edited_message` | 将用户任务消息的修改转换成事件 | 任务是否更新、重启或追加修正尚未确定 |
| `callback_query` | 将 `/choose` 转换成原按钮回调 | 需保留原始 callback_data 和菜单上下文 |
| `answerCallbackQuery` | 确认本地选择处理结果 | 没有 Telegram 原生回调提示界面，具体反馈待定 |
| 菜单、按钮更新 | 更新菜单映射及消息末尾指令 | 需处理旧菜单失效及按钮类型差异 |
| 输入中、草稿、流式回复 | 状态消息或合并编辑等方式 | 体验和语义无法直接等同，方案待定 |
| 文件上传与下载 | Teams 附件或 SharePoint 等底层 | 尚未确定桥接方案；需映射文件对象和下载路径 |
| Telegram 话题及多个 OMP 会话 | 会话标记或命令路由等方式 | 不直接照搬；第一版范围待确认 |

不能把未知或未实现的有副作用方法统一返回成功。哪些辅助方法可作为明确的空操作，需结合插件实际使用方式确定。

## 6. 消息身份、去重与恢复约束

Teams 自聊中的用户消息和服务消息都由同一个 Teams 账号发送。`/chat` 与 `omp：` 明显降低了来源识别复杂度，但仍需要持久化记录以支持编辑、删除、重复输入和重启恢复。

拟记录的信息包括：

| 信息 | 用途 |
|---|---|
| Teams 消息 ID | 精确定位消息，识别修改和删除 |
| 虚拟 Telegram message_id | 支持插件回复、编辑及删除对应消息 |
| 用户／服务来源 | 防止服务输出被当作用户输入 |
| 正文及版本信息 | 检测修改，保留消息身份 |
| update_id | 为插件提供更新序列及确认游标 |
| 队列与发送状态 | 记录待处理、处理中、已完成或结果未知 |
| 菜单与选项映射 | 精确转换用户选择 |

关键约束：

- 不能只用正文相同判定重复消息；用户可能合法地连续发送相同指令。
- 同一条 Teams 消息被反复观察时，不能反复触发任务。
- 首次接入应建立历史基线，避免将已有自聊记录全部提交给 OMP；具体历史起点规则待定。
- 服务重启后不能重新执行已处理指令。
- `getUpdates` 必须遵循所选兼容范围的确认规则，不能一返回就不可恢复地删除更新。
- 发消息前记录发送任务，发出后关联实际 Teams 消息 ID。
- 对发送结果未知的情况，先核对是否已发出，再决定重试，防止重复回复。
- 不承诺只依靠浏览器操作即可天然获得端到端严格一次执行；恢复与去重需通过实际故障测试验证。

## 7. 选择菜单的状态约束

- 菜单编号应能区分同时存在的多个菜单和历史菜单。
- 每个选项保存原始 callback_data、原消息及所属交互上下文。
- 选择只作用于明确匹配的菜单和选项，不按显示文字模糊匹配。
- 已替换、已删除或所属会话已结束的菜单不能误触发新任务。
- 一次性确认选项与翻页、刷新等可重复操作应区别处理，不能全部统一为只能点击一次。
- 菜单更新时需同步更新指令呈现和本地映射，避免显示内容与实际选项错位。
- 菜单有效期、编号格式、并发选择、失效提示及回复是否标注“已选择”，尚未确定。

## 8. 修改与删除的语义边界

### 8.1 修改用户指令

用户指出 Teams 支持修改已发送消息，但尚未确认如何将修改应用于 OMP 任务。

待确定的情况：

- 尚未开始的任务，修改原消息是否更新排队内容。
- 正在执行或已完成的任务，修改是否形成后续修正、重新执行，还是不再处理。
- 普通消息被编辑成 `/chat` 是否作为新的提交。
- `/chat` 消息被编辑为普通消息是否影响已有任务。
- 连续编辑如何合并，以及插件本身如何处理 edited_message。

“第一版只接受新发送的指令”是讨论中的简化建议，尚未作为用户最终要求确认。

### 8.2 修改和删除 OMP 回复

- 按虚拟消息 ID 找到实际 Teams 回复进行操作。
- 编辑时保留 `omp：` 前缀。
- 对服务自己的回复进行修改，不生成用户任务事件。
- 不能因为 API 客户端传入任意消息 ID 就修改或删除无关的用户记录。
- 实际编辑、删除结果应在页面确认，不能仅凭点击按钮就返回成功。

### 8.3 用户删除指令

普通 Telegram 私聊没有通用的消息删除通知。参考插件的轮询代码也明确指出这一限制，因此不能将 Teams 删除动作直接视为未修改插件已支持的取消任务事件。

- 用户删除 Teams 指令，不自动等价于取消 OMP 任务。
- 如果需要“删除指令即取消排队任务”，应增加明确的插件或控制层适配。
- 删除聊天消息不能保证撤销已发生的项目修改或外部操作。
- 使用明确停止／取消指令是已提出的建议；具体名称、是否必须加 `/chat` 及取消范围尚未确认。

依据：[参考插件的轮询代码](https://github.com/evandrodevbr/oh-my-pi-telegram/blob/main/lib/polling.ts)。

## 9. 本地浏览器服务的运行约束

已验证的网页操作使用 Edge 已登录会话，通过浏览器扩展读取页面结构并操作输入框、按钮和文件选择器。

常驻服务还需处理：

- Teams 页面刷新、DOM 更新及选择器变化。
- 消息列表局部加载、虚拟化和历史消息重新渲染。
- 登录过期、浏览器关闭、网络中断、电脑休眠及恢复。
- 用户同时操作自聊窗口、存在草稿或切换会话。
- 短时间内新增、编辑或删除消息造成的观察竞态。

不能将“某条消息当前不在 DOM 中”直接判定为已删除，也不能仅用定时读取全文再比较差异代替可靠的消息事件系统。

必须验证页面中能否取得稳定消息 ID、编辑状态和删除状态，并明确浏览器观察范围外的事件是否能够补取。所需专用扩展、独立浏览器适配器或其他连接方式尚未选定。

当前 Codex 操作工具和已编写的 skill 证明了交互操作可以完成；它们本身不是已经实现并验证的常驻后台服务。

## 11. 已完成的实测及证据边界

| 项目 | 实测结果 |
|---|---|
| Edge 中定位 Teams | 找到并读取当前账号自聊 `SELF_CHAT_DISPLAY_NAME(你)` |

## 12. 首轮实现建议与待确认事项

首轮建议先实现单个自聊、单个 OMP 会话、`/chat` 任务提交、带 `omp：` 的最终回复和 `/choose` 选项转换，再验证消息编辑和恢复能力。菜单所需辅助 API 必须按实际插件补齐，不能仅实现 sendMessage 就声称插件全部可用。

以下为待定项，不应自行固化为用户已批准的要求：

1. 实际使用的 OMP Telegram 插件、版本及运行环境。
2. OMP 与浏览器服务是否在同一台电脑，以及网络连接方式。
3. 服务的语言、框架、数据库、端口、启动方式和认证方式。
4. `/chat`、`/choose` 的精确语法和异常输入处理。
5. 是否支持停止／取消指令及其格式和作用范围。
6. 用户编辑或删除任务消息时的业务行为。
7. 菜单生命周期、重复选择和非回调按钮支持范围。
8. 流式回复、输入中提示和状态消息的呈现方式。
9. 多会话、话题和文件传输是否属于第一版。
10. 初次接入及离线恢复的消息起点、补取范围和保留期限。
11. OMP 原有指令清单、插件现有支持范围及缺失指令的适配方式。

## 13. 拟验证的验收场景

- 普通自聊消息不触发 OMP；`/chat` 新消息能触发一次任务。
- `/chat /对应指令 [参数]` 保留内部指令及参数，并进入原有指令处理机制；无 `/chat` 前缀的原有指令不触发。实际指令效果需逐项验证。
- 服务回复以 `omp：` 开头，回复和其中列出的指令不会形成输入回路。
- `/choose` 能准确还原对应菜单的原始回调数据；旧菜单不会错误作用于新菜单。
- 相同正文的两条独立用户指令按两条消息处理；同一消息重复观察不重复执行。
- 服务或插件重启后不重放已完成任务，也不丢失尚未确认的更新。
- 发出回复后出现连接中断或进程退出，恢复时不盲目重复发送。
- 插件所有启用的 API 路径均进入本地服务，完成一次真实 OMP 任务的输入与回复。
- 编辑、删除和文件能力按最终确认范围分别验证；未实现的能力不返回虚假成功。

以上场景是基于讨论提出的验证建议，最终验收范围需与确定的第一版功能一致。
